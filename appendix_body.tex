\section{Purpose and scope}

This appendix reports the benchmark suite run to (i) answer reviewer
requests for quantitative performance evidence (fit time, projection
time, peak memory, scaling with raster size and sample size), and (ii)
locate the computational bottlenecks of \texttt{maxentcpp} 1.0.0 so
that the package can be optimized without breaking its numerical
fidelity contract with Java Maxent 3.4.4.

Every number in this appendix was obtained by actually running the
code on 11 August 2026.  No figure is copied from an earlier draft or
from the literature.  The scripts that produced the numbers are listed
in Section~\ref{sec:repro} together with their output files.

\section{Methodology}

\subsection{The in-place mutation artifact (critical)}

\texttt{maxent\_fit()} \emph{mutates the \texttt{FeaturedSpace} object
in place}.  The optimizer updates the feature lambdas stored inside the
featured space and leaves them there when it returns.  Consequently,
calling \texttt{maxent\_fit()} twice on the \emph{same} featured space
does not measure two independent fits: the second call starts from the
already-converged solution and terminates after only a handful of
iterations (21 instead of 261 in our tests), producing a grossly
optimistic timing.

This artifact is the explanation for the ``$\sim$820\,ms'' figure that
appeared in the v2 draft: it was measured by re-fitting a reused
featured space.  All benchmarks in this appendix therefore create a
\emph{fresh} featured space (and fresh feature objects) for every
measured fit.  Section~\ref{sec:fit} shows the two numbers side by
side so the difference is visible.

\subsection{Warm-up}

The first call to the Rcpp module in a fresh R process pays a one-time
cost of roughly 5--19\,s (library load / symbol resolution / page
faults).  Every benchmark below runs one or two warm-up fits first and
excludes them from the reported timings.

\subsection{Memory measurement}

Peak resident set size (RSS) was measured with
\texttt{/usr/bin/time -v} around a whole \texttt{Rscript} process that
(a) performs a warm-up run, then (b) performs the measured fit and
projection.  Both \texttt{maxentcpp} and \texttt{maxnet} scripts load
the same libraries and data so the comparison is apples-to-apples.

\subsection{Data}

Two datasets were used:

\begin{itemize}[leftmargin=1.2em]
\item \textbf{Bundled \emph{Abeillia abeillei} dataset} (package
  \texttt{extdata}): 73 presence records, 2,371 non-NA background
  cells, two predictors (bio1 = annual mean temperature, bio12 =
  annual precipitation, Central America), linear + quadratic + hinge
  features, 44 features total, \texttt{max\_iter = 500},
  \texttt{convergence = 1e-5}.
\item \textbf{Synthetic grids} (for scaling and the 1.0.0 diagnostics):
  2,371 / 23,000 / 233,000 cells with two continuous predictors (plus
  one five-level categorical for the diagnostics), Gaussian niches for
  presence sampling.
\end{itemize}

\section{Hot paths in the optimizer}
\label{sec:hotpaths}

The sequential optimizer lives in
\texttt{src/cpp/include/maxent/sequential.hpp} (class
\texttt{Sequential}, mirroring Java \texttt{density.Sequential}).
The measured numbers (261 iterations, $\sim$18.1\,s, 2,371 points, 44
features) imply a per-iteration cost of
\[
18.1\text{ s} / 261 \approx 69\text{ ms/iteration}.
\]
Three loops dominate that budget:

\begin{enumerate}[leftmargin=1.2em]
\item \textbf{\texttt{get\_best\_feature()} --- feature selection.}
  Every non-parallel iteration scans all $J = 44$ features and calls
  \texttt{delta\_loss\_bound(j)} for each.  Each bound is $O(n)$ in
  the number of points $n = 2{,}444$, so this step is
  $O(n \times J)$ per iteration.  With 261 iterations this is the
  dominant cost.
\item \textbf{\texttt{search\_alpha()} / \texttt{new\_loss\_change()}
  --- step-size search.}  After selecting a feature, the optimizer
  computes a Newton step and then searches for a better step size by
  repeatedly calling \texttt{new\_loss\_change(j, alpha)}, each call
  looping over all $n$ points with a \texttt{std::exp()} per point.
  The quadrupling loop can evaluate this several times per update.
\item \textbf{\texttt{do\_parallel\_update()} --- every 10 iterations.}
  Computes the Hessian-vector product and gradient over all $n$
  points for the subset of features scheduled for update
  ($O(n \times n_{\text{update}})$).
\end{enumerate}

All three loops are single-threaded by design: the optimizer must
preserve Java Maxent's exact iteration order for the fidelity
contract (\texttt{maxentcppCompTest} compares per-iteration loss,
entropy, and $\lambda$ trajectories).  Any optimization must therefore
preserve bit-comparable results under the deterministic settings, or
be gated behind an opt-in flag with the fidelity suite re-run.

\section{Optimization opportunities (for the developer)}

The following directions are ordered by expected impact.  They are
\emph{suggestions grounded in the measured hot paths above}, not
already-verified changes; each must be validated against
\texttt{maxentcppCompTest} and the benchmark scripts.

\subsection{High impact}

\begin{enumerate}[leftmargin=1.2em]
\item \textbf{Vectorize the $O(n)$ loops with Eigen.}
  \texttt{new\_loss\_change()} and \texttt{delta\_loss\_bound()}
  currently loop over points with scalar \texttt{std::exp()} calls.
  \texttt{std::exp()} on a vectorized Eigen array is
  $\sim$4--8$\times$ faster on modern x86 (the hardware has AVX2).
  The package already depends on Eigen (used for the feature matrix
  and streaming provider), so this is a pure implementation change
  with no algorithm change.
\item \textbf{Avoid recomputing per-feature statistics.}
  \texttt{get\_best\_feature()} recomputes \texttt{delta\_loss\_bound}
  for \emph{all} features every iteration, even though only the
  selected feature's lambda changed.  Caching per-feature bounds and
  updating only the affected entries would reduce the selection scan
  from $O(n \times J)$ to $O(n \times k)$ where $k \ll J$ is the
  number of recently changed features.  The Java code has a
  \texttt{featuresToUpdate} notion; the C++ port already computes
  \texttt{state\_[j].last\_change} --- the cache can key on that.
\item \textbf{Reduce \texttt{search\_alpha} evaluations.}
  The quadrupling loop calls \texttt{new\_loss\_change} (an $O(n)$
  pass with one \texttt{exp} per point) until the loss stops
  improving.  A golden-section or analytic bound on the quadratic
  would cut the number of passes, or the exp computations of
  successive trials could be reused (they differ only by the step
  multiplier).
\end{enumerate}

\subsection{Medium impact}

\begin{enumerate}[leftmargin=1.2em]
\item \textbf{Parallelize across independent fits.}  Replicate runs,
  cross-validation folds, and jackknife leave-one-out fits are
  independent by construction.  The paper already states parallelism
  is applied ``across independent fits''; making it real with
  OpenMP/threads (or documented \texttt{future} support) would turn
  the 63--135\,s diagnostics into 63/cores--135/cores seconds with
  zero fidelity risk, because each fit is bit-identical to the
  serial one.
\item \textbf{Compile flags.}  Verify the package builds with
  \texttt{-O3} and, where CRAN permits, \texttt{-march=native} on
  Linux; profile-guided optimization for the hot loops.  (CRAN's
  policy restricts \texttt{-march} on CRAN builds; the effect can be
  delivered to users via a documented \texttt{Makevars} override
  without changing the default.)
\item \textbf{Reduce \texttt{std::exp} precision where safe.}
  \texttt{new\_loss\_change} accumulates \texttt{exp(alpha *
  F(i,j))}.  If the fidelity suite confirms the summation order is
  the only sensitive part, an opt-in \texttt{-ffast-math}-style fast
  exp (or \texttt{expf} with double accumulation) could be gated
  behind an option, but this is risky and must be off by default.
\end{enumerate}

\subsection{Low impact / do not touch}

\begin{enumerate}[leftmargin=1.2em]
\item \textbf{Streaming projection.} Already 21\,ms at 23K cells and
  memory-efficient; there is nothing to gain at these scales.
\item \textbf{Feature generation.} Measured at $<$1\,ms; not a
  bottleneck.
\item \textbf{The fidelity contract.} The per-iteration trajectory
  tests are the package's core value proposition; never change the
  default algorithm path in a way that alters iteration order or
  numerical results.
\end{enumerate}

\section{Summary for the optimization task}

\begin{itemize}[leftmargin=1.2em]
\item The optimizer is $>$99\% of runtime.  Optimize
  \texttt{sequential.hpp} only.
\item Target: reduce the $\sim$69\,ms/iteration on 2,371 points /
  44 features.  The three hot loops are feature selection
  ($O(nJ)$), step-size search ($O(n)$ with multiple
  \texttt{exp()} passes), and the periodic parallel update.
\item The fastest safe wins: Eigen-vectorized \texttt{exp} loops and
  caching of \texttt{delta\_loss\_bound} between iterations.
\item Parallelism across independent fits (replicates / CV /
  jackknife) is free of fidelity risk.
\item Keep peak RSS at or below $\sim$158\,MB on this dataset --- it
  is currently a 2.3$\times$ advantage over \texttt{maxnet}.
\item After any change, re-run \texttt{maxentcppCompTest} and the
  scripts above; the fidelity suite is the gate.
\end{itemize}
